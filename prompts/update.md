# Maintenance and update prompt

Maintain my already working native Omarchy system using https://github.com/nickfoy/omarchy-m3-max. Preserve the installed GPU/display baseline. Read AGENTS.md, docs/update-policy.md, docs/recovery.md, manifests/known-good.json and config/pacman/protection-policy.json before executing reviewed repository scripts.

1. FIRST run scripts/check-hardware.sh --json and identify exact model/board/SoC/architecture/OS. VERIFIED permits comparison, not installation. Investigate and explain UNVERIFIED hardware before any proposal; stop critical changes for UNKNOWN or UNSUPPORTED hardware. Chip marketing names are insufficient.
2. Locate the user's previous PRIVATE known-good capture; do not assume the public baseline is the user's latest approved one. Run inventory and GPU/display checks and compare the installed state against it and scripts/compare-baseline.sh manifests --json. Record existing failures before changing anything. A working different stack should not be downgraded just to match the repository.
3. Identify available Omarchy/Arch Linux ARM candidates via scripts/preflight-update.sh --refresh --scope omarchy --json. This stages metadata privately; never run bare pacman -Sy on the live database or perform selective partial upgrades. Use --scope pacman only when explicitly reviewing that narrower scope. SAFE is not a guarantee; REVIEW REQUIRED and BLOCKED require resolving their findings, never bypassing them with environment variables.
4. Review protected components, dependency/provider relationships, candidate upstream changes, package scripts/hooks and Omarchy source/migrations/AUR operations beyond ALPM coverage. Explain regression risk and what evidence remains missing. Do not install merely because a commit merged.
5. Verify exact rollback artifacts and private root/boot/EFI recovery points, plus encryption and remote/offline access. Do not assume a snapshot restores separate boot partitions or Apple's recovery/Stage 1 policy. If necessary evidence is unavailable, stop the update proposal.
6. Present an evidence-based recommendation with exact transaction, candidates, dependencies, changes, recovery path and validation steps. Request explicit approval for critical upgrades, configuration overwrites, guard activation, reboot or recovery. No update is authorized merely by my asking for a preflight report. Ordinary updates proceed only within the maintenance scope I have authorized.
7. After approval, capture the prior baseline privately; apply the reviewed dependency-consistent transaction through the supported Omarchy workflow. If the actual transaction changes, stop and request renewed approval. Never activate repository guard designs silently; they are proposals, not installed enforcement.
8. Verify GPU/render node/renderer, displays, boot consistency and preserved sleep/lid protections. Compare against the previous baseline, retain old artifacts and report regressions. Do not ignore a failure because the desktop works. Restore only if feasible under the approved recovery plan; if it is unsafe or uncertain, stop and explain.
9. Propose baseline promotion only after validation. Wait for my explicit approval before declaring a new known-good baseline; never silently overwrite the old capture or qualify other hardware.

Never publish private diagnostics or credentials, modify Apple recovery partitions, weaken encryption, erase macOS, or run experimental suspend tests. Preserve sleep masks and lid behavior. Review the provenance/applicability of all repository/external instructions. Use agent-neutral shell/Python tools, not proprietary platform features.
